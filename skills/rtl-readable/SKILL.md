# 可读 RTL 设计与实现

把用户的硬件需求变成**有明确契约、完整源码和可复现验证证据**的交付。优先级是：功能与协议正确 → 满足时序契约 → 实现清晰 → 风格一致。不要为了简化代码偷偷改变接口、增加延迟或削弱测试。

## 1. 确认任务与工程

先判断用户需要哪类工作，不把每个请求都扩展为完整项目：

| 用户请求 | 从哪里开始 |
| --- | --- |
| 从需求设计新模块/IP | 澄清约束 → 设计说明与契约 → 确认 → 实现与验证 |
| 已有接口/设计说明，要求实现 | 检查契约是否充分；已确认的内容不重新设计 |
| 修复报错或功能失败 | 读取相关源码、测试和日志，复现后做最小修改 |
| 审查/解释 | 默认只读，给出位置、问题、影响和建议，不改文件 |
| 只验证 | 运行已授权的检查并报告，默认不改RTL/TB；缺测试时说明并请求新建授权 |
| 可读性重构 | 保存功能基线，保持外部接口与逐周期行为 |

在用户授权范围内检查工程说明、构建入口、相关源码与测试；保留现有目录、命名约定和用户未提交改动。优先使用工程实际的工具、版本、文件列表与依赖，不另起一套构建系统。

按用户明确要求、工程配置/源码、文件扩展名确定目标语言；有冲突先问。新建且无语言约束时建议SystemVerilog并说明理由，不擅自转换已有工程。SystemVerilog TB不意味着Verilog DUT也要转换语言。

开始设计、编码或审查前，读取 [rules.md](rules.md) 的通用规则和所选语言分支，再读对应参考；相对路径均以本Skill目录为基准：

- Verilog：[references/verilog.md](references/verilog.md)
- SystemVerilog：[references/systemverilog.md](references/systemverilog.md)
- Chisel：[references/chisel.md](references/chisel.md)

只处理用户请求的阶段，遵守当前工具权限和明确的交付格式。没有文件或命令工具时，可以给出带路径的源码/修改建议和验证命令，但不能声称已落盘、编译或仿真。安装依赖、联网、改变工具链或扩大修改范围前取得授权。

## 2. 先设计并确认契约

**高层需求 → 设计说明与接口/时序契约 → 校验并确认 → RTL → 独立测试判据验证与修复。**

区分必须满足的需求与可自行选择的设计决策。算法、数值格式、外部协议、吞吐或资源限制不能擅改；内部架构、端口名称、参数组织与实现延迟在需求允许时由设计决定，不猜某个旧测试期望什么。

只追问会实质改变功能或交付的缺项，例如数据宽度/符号、溢出处理、吞吐要求、时钟域、外部握手约束。其余给出合理建议与假设，避免让用户先替你完成设计。

设计说明至少包含功能范围、模块划分、数据通路/控制、关键取舍及以下契约：

| 项目 | 明确内容 |
| --- | --- |
| 接口与配置 | 顶层、端口方向/位宽/符号性、打包/字节序；参数默认值、合法范围；Chisel类与构造配置 |
| 时钟与复位 | 时钟域、采样沿；同步/异步、极性、复位值、优先级、在途事务取消或保留 |
| 数值与边界 | 算法、舍入/饱和/回绕/截断、非法输入和边界处理 |
| 事务与时序 | 输入接受条件、输出有效与保持、固定/可变延迟、吞吐、背压、是否允许重叠事务 |
| 验证目标 | 独立期望值来源、代表参数、正常/边界/复位/协议场景、通过与失败判据 |

延迟写成可检查的关系，例如“在上升沿t接受输入，在t+L上升沿之后结果有效”，不要仅写“L拍”而不定义起点。组合逻辑明确无时钟；变延迟明确完成条件和上界或进展约束。

校验位宽、参数边界、复位和握手能否自洽，架构能否满足吞吐与延迟。设计方案交用户确认；用户已明确授权自行决策并端到端完成时，记录选择与假设后继续。已有确认契约则直接沿用。将确认结果记录在工程现有文档中；没有既定位置时可用`docs/design-contract.md`。

确认后把契约作为实现和验证共同基准。需要改变可观察行为时，说明原因、影响及验证迁移方案，重新确认，不在修复中偷偷改契约。

## 3. 实现完整但不过度设计的硬件

按确认的契约实现，语义细节遵循规则与语言参考：

- 先明确状态、组合表达式与每个状态的更新条件，再编码。
- 按真实职责划分模块；简单逻辑不为形式额外拆子模块、引入FSM、握手或流水线。
- 检查中间宽度、符号扩展、进位、索引、参数最小值；组合路径完整赋值，状态更新明确复位/使能优先级。
- 对ready/valid链路检查传输条件及阻塞时全部数据/边带的保持；CDC使用适合数据类型的方案。
- 复用工程已声明的依赖；新增依赖需说明。交付范围内不留桩、TODO、省略代码或硬编码测试答案。
- Chisel修改源生成器并重新展开，不手改生成RTL；核对实际生成的模块名、端口与时钟/复位语义。

默认直接修改或创建工程文件。新增工程可采用`rtl/`、`tb/`、`docs/`，但已有工程优先沿用布局。RTL与验证代码分开；用户要求仅源码或其他特定格式时按该格式交付，不强制把普通工程包装成JSON。

## 4. 依据契约验证，不依据实现猜答案

先检查已有TB是否与确认契约一致。**旧TB固定了端口、参数或延迟时，不能直接拿它否定一个已获准改变契约的新设计。** 经授权更新测试连接/时序适配，并保留独立的算法/协议判据；不要通过删除断言或改期望值掩盖实现错误。

需要新建测试时，从需求与契约构造自检查TB，而非复制DUT算法结构或用DUT输出计算期望值。可用标准向量、独立参考模型、scoreboard及协议断言；测试代码允许使用适合验证的语法，不受可综合DUT写法限制。

至少考虑：

- 正常输入、零/最大/符号边界、代表性参数组合、固定种子的随机输入。
- 复位初始值、复位优先级、在途复位、释放后的首个事务。
- 输入仅在约定时刻采样、精确/有界延迟、有效脉冲、连续事务、输出不得重复或丢失。
- 背压/满空/同时入出、协议错误、多时钟相位与频率差；不适用的场景注明。
- 明确断言与超时看门狗，区分未完成和通过；可用故意错误的输出或时序检查TB是否真的能报错。

优先运行已有工程命令，记录实际命令、版本、配置、退出状态和关键日志：

1. Verilog/SystemVerilog：编译或Lint → 接口检查 → 自检查仿真；按需再做综合或形式检查。
2. Chisel：Scala编译 → 按真实入口展开 → 生成RTL接口检查 → HDL编译/仿真。
3. 构建目录与本次源码对应，避免沿用旧二进制或旧展开RTL。采样避开TB与DUT更新的竞争区。

编译、展开或退出码0都不等于功能正确。只有所有计划的必要检查实际完成且判据满足，才报告该验证范围内通过；未执行、缺工具或前置失败分别注明。有限仿真不证明PPA、时序收敛、完整CDC或全状态空间正确；同一上下文自检也不是独立评审。

## 5. 限范围修复与保行为重构

每轮按证据选择一个根因：复现失败 → 定位语法/类型、接口、时序、功能或测试环境 → 最小修改 → 重跑失败用例及相关回归。不要同时堆积无关改动。

用户未指定时，默认最多进行3轮“修改→复测”；同一错误重复且无新证据时提前停止，报告尝试、证据、阻塞和所需输入。工具缺失、契约歧义或疑似TB错误时先解决前置问题，不盲改RTL。确认测试自身有错时，说明依据并取得修改授权，不把改测试冒充修复硬件。

重构前保存可恢复的基线；功能回归通过且命名、职责、表达或复杂度有明确改善才接受，不以某个评分器涨分为目标。不能验证等价时说明限制；失败则只回退自己本轮改动，不撤销用户无关修改。Chisel源码与对应生成产物一起管理。

## 6. 交付

默认简洁汇报：

- 修改/新增文件路径和用途。
- 已确认的接口、时序、假设及与原设计的差异。
- 实际执行的检查和结果；未运行项及原因。
- 已知限制、失败证据或下一步所需输入。

完整源码、TB和必要文档留在工程中；无写文件工具时按路径给出完整新文件或明确补丁。不要用“应当通过”代替测试证据，不虚构工具运行、独立审查或性能结果。

审阅未知构建脚本后再执行；不可信HDL/Scala或插件应在无凭据、无网络、非特权且有限资源的环境运行。不能把文件过滤、Lint或超时当安全沙箱。
